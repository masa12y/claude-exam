# マルチモーダルとバッチによる取り込み

- 画面数：3画面（教育13分、注意点4分、チェックポイント3分）

---

## 画面1：教育（13分）
### 画像、PDF、大量処理

これまでは、ターン間でClaudeが何を記憶しているかを管理してきました。マルチモーダルによる取り込みでは、問いが「何を送り込むか」へと変わります。すべての画像とPDFは、Claudeがプロンプトの文字を1文字も読む前からコンテキスト予算を消費し、これによってリクエストの構成方法や、1回のリクエストに収められる内容が変わってきます。

このトピックの後半では、同じ問題の反対側を扱います。処理すべき入力が数千件ある場合、1件ずつリクエストを送って応答を待つという方法は意味をなさなくなります。Message Batches APIは、アプリケーションを止めることなくその量を処理するための方法です。

---

### 画像のトークンコスト：決定する前に計算する

画像は、コンテキスト予算の観点では無料ではありません。Claudeは画像をパッチ単位で見ます。画像の28×28ピクセルのブロック1つが1つのビジュアルトークンとなり、画像のコストは `⌈幅 / 28⌉ × ⌈高さ / 28⌉` ビジュアルトークンになります。

- **計算例**：1,000×1,000ピクセルの画像は、`⌈1000/28⌉ × ⌈1000/28⌉ = 36×36パッチ`、つまり約1,296ビジュアルトークンになります。
- この割合では、高解像度のスクリーンショット10枚が、詳細なシステムプロンプトと同程度のコンテキストを消費します。
- 各モデルには、長辺の上限とビジュアルトークンの上限として表される、ネイティブな画像解像度の上限もあり、これらの上限はモデルの階層によって異なります。最新モデルは、標準の階層よりもかなり大きな画像を受け入れます。
- いずれかの上限を超える画像は処理前に縮小されるため、この計算式は縮小後の寸法に対して適用されます。
- 実装時には、Visionのドキュメント（解像度とトークンコスト）で現在の階層別の上限を確認してください。この上限はモデルの世代間で変化してきており、今後も変わる可能性があります。

この計算は設計時に重要です。画像を処理するパイプラインを構築する場合は、取り込み用のコードを書く前に、典型的な本番用画像のトークンコストをモデルのコンテキスト上限と比較して測定してください。予算を超えたパイプラインの修正は、多くの場合、10分程度で済む画像のリサイズのステップです。デプロイ後にこれに気づいた場合は、さらに時間がかかります。

### 画像を送信するさまざまな方法：それぞれが適切な場面

| 送信方法 | 仕組み | 負担 | 使うべき場面 |
| :--- | :--- | :--- | :--- |
| **インラインのbase64** | 画像のバイトデータをbase64文字列としてエンコードし、そのデータをメッセージブロックに直接含める。 | エンコードされたペイロード全体がリクエストごとに送信されるため、リクエストサイズが膨らみ、大きな画像ではレイテンシに影響する。 | アップロードのステップを追加しても見返りのない複雑さが増すだけになる、一度限りの画像に最適。同じ画像を繰り返し送信するとコストが増していくため、再利用が見込まれる場合は別の方法を選択する。 |
| **URL参照** | `source` ブロックに公開アクセス可能なURLを渡し、Claudeがリクエスト時にその画像を取得する。 | リクエストにペイロードは含まれないが、そのURLがClaudeが取得を試みる時点で安定していて、公開されていて、到達可能である必要があるという依存関係を負う。 | 自分が管理する安定した公開URLに、既に画像がホストされている場合に最適。認証が必要なもの、短い有効期限付きの署名があるもの、リクエストの実行時に到達可能であると保証できないものには使用しない。 |
| **Files API** | 別のAPI呼び出しを通じてファイルを一度アップロードし、`file_id` を受け取り、以降のあらゆるメッセージでそのIDを参照する。 | アップロードは一度限りのコストであり、以降のすべてのリクエストはバイトデータの代わりにIDを運ぶだけになるため、その時点からペイロードの負担はほぼゼロになる。現在ベータ版であり、BedrockやVertex AIでは利用できない（デプロイ先プラットフォームでの利用可否を確認すること）。 | 同じ画像やPDFが複数のリクエストにわたって使われる場合、または再送信するとリクエストサイズの大部分を占めてしまうほどアセットが大きい場合に最適。アセット管理を推論の呼び出しとは別に扱いたい場合や、複数の会話ターンにわたって使われる画像にも適している（履歴が増えても `file_id` はペイロードの重さを増やさないため）。 |

### PDFの送信：documentブロック

PDFの場合、ブロックタイプは `image` ではなく `document` になります。

- `source` の構造は画像と同じパターンに従うため、base64、URL、またはFiles APIの `file_id` のいずれかを使用できます。
- `document` ブロックには、必須の `name` フィールドはありません。
- 読みやすいドキュメント名のための任意の `title` フィールドと、追加のメタデータのための任意の `context` フィールドを受け付けますが、PDFを送信するためにどちらも必須ではありません。
- トークンコストの考慮事項やFiles APIによる再利用を含む、その他の仕組みはすべて同じように適用されます。

```json
{
  "type": "document",
  "source": {
    "type": "base64",
    "media_type": "application/pdf",
    "data": "<base64-encoded-pdf-bytes>"
  },
  "title": "contract_review.pdf"
}
```

### マルチモーダルな入力へのプロンプティング技法の適用

最初のセクションで扱ったのと同じプロンプティングの技法が、画像やPDFの分析にも適用されます。「この画像を説明してください」という素のプロンプトが浅い出力を生むのは、素のテキストプロンプトが浅い出力を生むのと同じ理由です。Claudeが目指すべき対象の構造を持っていないためです。

違いは、画像がテキストにはない曖昧さを伴うことです。それには、重なり合う物体、奥行きや空間的な関係、部分的な隠れなどが含まれます。視覚的な分析のためのプロンプトは、それぞれの種類の曖昧さをClaudeがどのように扱うべきかを明示すべきです。

> **具体例**：「物体が重なっている場合は、それぞれを別々に説明し、重なりについて記述してください」は、テキストのみのプロンプトでは決して必要にならない、具体的な制約です。

### Message Batches API：大量の非同期処理

同じプロンプトのパターンを数百件や数千件の入力に対して実行する必要がある場合、同期型のAPIは適したモデルではありません。同期呼び出しはそれぞれ、完了するまで処理をブロックします。規模が大きくなると、これはアプリケーションがスレッドを消費し続けるか、レートリミットに対して数千の同時接続を実行することを意味します。

- **仕様**：1回のバッチ呼び出しで、最大10万件、または256MB（どちらか先に達した方）までのリクエストを受け付けます。
- **処理の流れ**：バッチを送信し、`batch_id` を受け取り、完了をポーリングします。バッチが完了したら、結果をダウンロードします。
- **コスト**：バッチリクエストのトークンあたりのコストは、同期リクエストよりも低くなります。
- **トレードオフ**：レイテンシです。バッチ処理は非決定的であり、最大24時間かかることがありますが、多くの場合はそれよりもかなり速く完了します。
- **適用対象**：オフラインのパイプライン、エバルの実行、データ処理のジョブに適しており、リアルタイムのユーザーとのやり取りには適していません。

| ユースケース | 適切なAPIパターン | 理由 |
| :--- | :--- | :--- |
| ユーザーが写真をアップロードし、即座の分類結果を期待している | 同期API | リアルタイムの応答が必要。対話的な用途では、バッチのレイテンシは許容できない。 |
| 夜間バッチのパイプラインが5,000件の顧客レコードを分類する | Message Batches API | レイテンシは制約にならない。バッチによるコスト削減と非同期処理の両方に価値がある。 |
| エバルの実行が、2,000件の例に対して新しいプロンプトをテストする | Message Batches API | リアルタイム性が求められないオフラインのタスク。バッチが正しいパターン。 |
| チャットボットがユーザーのメッセージへの返信を生成する | 同期API | ユーザーが待っている状態であり、バッチでは許容できない遅延が生じる。 |

### マルチモーダルとバッチが組み合うとき、組み合わないとき

この組み合わせは、同じアセットを再利用し、数千件の入力にわたって構造化された出力を必要とする、オフラインのワークロードに適しています。

> **典型例**：固定された分類体系に対して画像を分類する夜間バッチのパイプライン。Files APIが重複したアップロードを排除し、Batches APIがレイテンシを吸収し、構造化出力の技法が結果を機械可読なまま保ちます。

#### 組み合わせを崩す2つの失敗パターン

1. **レイテンシの見誤り**：画像を伴うユーザー向けのフローでバッチを使うと、テストには通るが本番環境では失敗するシステムができてしまいます。ユーザーは待っていますが、バッチはそうではないためです。
2. **コンテキストのコストを過小評価すること**：画像やPDFは、Claudeがテキストを処理する前から予算を消費するため、1回のリクエストで複数の大きな画像を読み込むパイプラインは、規模が大きくなるとトークンの上限を超えてしまいます。構築する前に、本番規模の入力でトークンコストを測定してください。

## 画面2：注意点（4分）
### 実はバッチではなかったバッチジョブ

#### 状況設定

ジョブをいくつかの塊に分割し、それらを順番に処理することはバッチ処理ではありません。それは、余分な手順が増えただけの逐次処理です。Message Batches APIが大量のワークロードのために存在するのは、まさに、同期APIに対して入力をループ処理すると、入力リストをどのように分割しても、量が本格的になった瞬間にレートリミットに突き当たるからです。

#### レートリミットに繰り返し突き当たる夜間バッチについての社内チャンネルでのやり取り

あるデベロッパーが、同じ夜間の分類ジョブを3晩にわたって再実行しており、毎回ほぼ同じ箇所でレートリミットのエラーに突き当たっています。シニアデベロッパーが、実際の問題を表面化させる1つの質問をします。

> **デベロッパー**：「夜間バッチがレートリミットに突き当たり続けています。すでに小さな塊に分割してみましたが、他に何ができるでしょうか。」  
> **シニアデベロッパー**：「それらをどのように送信していますか？」  
> **デベロッパー**：「リストをループ処理し、各項目についてAPIを呼び出しています。」  
> **シニアデベロッパー**：「それはバッチ処理ではありません。それは、同期エンドポイントに対する逐次呼び出しです。リストを塊に分割しても、APIから見える内容は変わりません。項目ごとに1つのリクエストが、次々と送られてくるように見えているだけです。」  
> **デベロッパー**：「つまり、数千回の同期呼び出しを行っているために、レートリミットが発生しているということですか？」  
> **シニアデベロッパー**：「そうです。Message Batch APIは、1回のバッチ呼び出しで最大10万件、または256MBまでのリクエストを受け付け、`batch_id` を返し、それらを非同期で処理します。完了はポーリングで確認します。つまり、コードがAPIから完了の通知を受けるまで、決まった間隔でバッチの状態を繰り返し確認するということです。トークンあたりのコストは同期呼び出しより低く、数千件の個別リクエストを行っているわけではないため、レートリミットも発生しません。」  
> **デベロッパー**：「トレードオフは何でしょうか？」  
> **シニアデベロッパー**：「レイテンシが非決定的であることです。バッチ処理には数時間かかることがあります。これがリアルタイムのユーザーとのやり取りであれば、誤った手段になります。しかし、夜間の分類バッチには最適です。」

#### 注意点のポイント

- リストを塊に分割して同期APIをループ処理することは、そうであるべきに感じられるとしても、バッチ処理ではありません。これは、分割しなかった場合と同じ数のAPI呼び出しを生み、同じレートリミットに突き当たります。
- Message Batches APIは、より小さなバッチサイズではなく、**異なる送信モデル**です。
- ワークロードが大量でオフラインである場合は常にこれを使用し、ユーザーが結果を待っている場合にのみ同期APIを使用してください。
- 結果は、リクエストを送信した順序ではなく、任意の順序で返ってきます。各リクエストの `custom_id` フィールドを使って、結果を元の入力に対応させてください。

## 画面3：チェックポイント（3分）
### 各シナリオに適した入力エンコーディングを選ぶ

以下の3つの入力シナリオについて、正しいエンコーディング方法を選びます。

#### シナリオ1：パイプラインのすべてのリクエストで使用される参照用の製品図

- 選択肢：
  - Message Batches API：すべてのリクエストを1回のバッチ呼び出しで送信し、完了をポーリングする
  - **Files API：一度アップロードし、各リクエストでfile_idを参照する（正解）**
  - インラインのbase64：エンコードし、メッセージブロックに直接含める
- **正解の理由**：インラインのbase64では、リクエストごとにペイロード全体を再送信することになり、呼び出しごとに転送の負担とレイテンシが加わります。

#### シナリオ2：サポートエンジニアが1回のリクエストで送信する、UIバグの単発スクリーンショット

- 選択肢：
  - Message Batches API：すべてのリクエストを1回のバッチ呼び出しで送信し、完了をポーリングする
  - Files API：一度アップロードし、各リクエストでfile_idを参照する
  - **インラインのbase64：エンコードし、メッセージブロックに直接含める（正解）**
- **正解の理由**：APIへのファイルアップロードは、一度しか使われないアセットのために、往復のステップを追加してしまいます。

#### シナリオ3：5,000件の顧客フィードバック回答を分類するジョブ

- 選択肢：
  - **Message Batches API：すべてのリクエストを1回のバッチ呼び出しで送信し、完了をポーリングする（正解）**
  - Files API：一度アップロードし、各リクエストでfile_idを参照する
  - インラインのbase64：エンコードし、メッセージブロックに直接含める
- **正解の理由**：同期APIでは、リクエストを逐次処理することになるか、レートリミットに対して数千の同時接続を管理する必要が生じます。
