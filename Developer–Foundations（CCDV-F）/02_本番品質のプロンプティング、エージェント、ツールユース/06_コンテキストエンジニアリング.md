# コンテキストエンジニアリング

- 画面数：3画面（教育16分、注意点5分、チェックポイント3分）

---

## 画面1：教育（16分）
### モデル選択と、複数ターンのセッションを予算内に収める方法

最初に行う選択は1つです。**どのモデルにワークロードを実行させるか**、です。Claudeのモデルファミリーは、コスト、レイテンシ、能力のトレードオフの幅を備えており、どのモデルを選ぶかによって、その後のすべての判断が動く範囲となる、価格とスピードの基準が決まります。

モデルが決まると、次の制約は**コンテキストウィンドウ**です。これは、プロンプト、それまでの会話、すべてのツール結果を含め、モデルが一度に取り込めるテキストの全体量を指します。Claudeが返すすべてのツール結果は、コンテキストウィンドウに追加され、セッションが続く間そこに残り続けます。

> **コンテキストエンジニアリング**とは、何をコンテキストウィンドウに入れ、何を要約として取り出し、何を最初から入れないのかを、事前に決める一連の判断のことです。

---

### モデル選択：Sonnetから始め、慎重に変更する

Claudeのモデルファミリーは現在、**Fable、Opus、Sonnet、Haiku** という4つの階層にわたっており、それぞれコスト、レイテンシ、能力のトレードオフに応じて最適化されています。

| モデル | 位置づけ |
| :--- | :--- |
| **Sonnet** | ほとんどの本番ワークロードに適した、バランスの取れた**既定の選択** |
| **Haiku** | 速度とコスト効率のために作られている。Sonnetの能力の範囲に収まるタスク向け |
| **Opus** | Sonnetの範囲を超える高度な作業向け |
| **Fable** | 複雑な推論、高度なコーディング、リサーチの統合など、最も要求の高いタスク向けのAnthropicの最高性能モデル |

> **実装時には、`platform.claude.com/docs` で現行のラインアップとモデル識別子を確認してください。**

#### モデル変更の判断基準

- **Opusへ移行**：エバルセットがSonnetでは品質基準を満たしていないと示した場合のみ
- **Haikuへ移行**：単にコストを抑えたいからではなく、エバルセットがそのタスクにおいて品質の低下が許容できると示した場合のみ
- モデルを変更する判断は、常に**根拠に基づいた判断**であるべきです

### コンテキストウィンドウは無限に使える資源ではない

コンテキストウィンドウは、Claudeが作業用の記憶として保持できる容量です。送信するすべてのメッセージ、返すすべてのツール結果、注入するすべてのドキュメント、Claudeが生成するすべての応答が、そのウィンドウの容量を占めます。

| 状況 | 結果 |
| :--- | :--- |
| リクエストがコンテキストウィンドウより大きい | Messages APIは生成の前に検証エラーとして拒否する |
| リクエスト自体は収まっても生成の途中で上限に達した | `stop_reason: model_context_window_exceeded` として返す |

> **注意：** どちらの経路も、古い内容を黙って切り捨てることはありません。セッションをウィンドウの上限を超えて続けたい場合は、次のリクエストを送信する前に、**アプリケーション側で履歴を削減または要約することで管理する**必要があります。

開発時には、テスト用の入力が小さくセッションも短いため、ウィンドウが満杯になることはほとんどありません。本番環境では、ツールの出力がテスト用のデータより3〜5倍長くなることが多く、ウィンドウは50ターン目ではなく8ターン目で満杯になります。

### 予算内に収めるための4つの戦略

| 戦略 | 内容 | 適用する場面 | 失われる連続性 |
| :--- | :--- | :--- | :--- |
| **プルーニング（枝刈り）** | 以前のメッセージまで戻り、そこから続ける。それより後の会話は削除される。 | Claudeが非生産的な方向に進んだ後、またはデバッグのやり取りが積み重なった後。 | 巻き戻した時点より後に行われた作業は失われる。 |
| **コンパクション**（Claude Codeでは `/compact`。APIではサーバー側コンパクション（ベータ版）または手動要約） | 会話履歴を、Claudeが学んだ重要な情報を保持したまま、圧縮された形に要約する。 | セッションがコンテキストの上限に近づいているが、積み重ねてきた知識を保ちながら同じ機能に取り組み続けたい場合。 | 要約の過程で詳細が失われることがある。 |
| **クリア**（Claude Codeでは `/clear`。APIでは新しいセッション） | 空のコンテキストで新しい会話を開始する。以前のセッションからは何も引き継がれない。 | 次のタスクが現在のタスクと完全に異なり、以前のコンテキストがバイアスや混乱を招くだけになる場合。 | セッションのコンテキストはすべて失われる。 |
| **サブエージェントへの引き渡し** | 必要なタスクの説明とシステムプロンプトだけを持った独立したコンテキストウィンドウの中にサブエージェントを生成する。サブエージェントが作業を行い、要約を返す。 | サブタスクが委任できる程度に自己完結している場合、特に探索的な作業の場合。 | サブエージェントがどのようにその結論に至ったかを把握できなくなる。 |

---

### さらに2つの手段：プロンプトキャッシュとトークンの計測

#### プロンプトキャッシュ

リクエストの変化しない先頭部分に対して行われた処理結果を保存し、以降のリクエストが同じトークンを再処理する代わりにそれを再利用できるようにします。

- **最も適した対象**：ターンをまたいでもほとんど変化しない部分（長いシステムプロンプト、大規模なツール定義の集合、繰り返し参照する資料）
- **有効化方法**：キャッシュ対象としたい最後のブロックに `type: ephemeral` の `cache_control` フィールドでキャッシュのブレークポイントを指定する（最大4つ）

#### トークンの計測

`count_tokens` エンドポイントは、`messages` 呼び出しと同じリクエストボディを受け取り、推論を実行せずにトークン数を返します。

| 用途 | 目的 |
| :--- | :--- |
| **開発時** | 実際のツール出力に対してコンテキスト予算の前提が成り立つかを確認する |
| **本番環境** | エラーになる前にウィンドウを超えるリクエストを事前に止める |

### RAGの経路が破綻しうる3つの箇所

| 箇所 | 問題 | 対処 |
| :--- | :--- | :--- |
| **チャンク分割** | 小さすぎると周辺コンテキストが不足し、大きすぎると関係のないテキストが混ざる | 文単位またはセクション単位で、少しの重複を持たせたチャンク分割を基本とする |
| **エンベディングによる一致** | 意味的に近い内容を取得するため、正確な語句を含む内容を取り逃すことがある | 意味的な一致と並行して、字句そのものの一致による検索も行う |
| **組み込みのステップ** | 取得したチャンクを想定する構造で渡さないと、モデルは自身の記憶から答えてしまう | プロンプトが想定する構造でモデルに渡す |

**一度だけ取得 vs 複数ラウンド検索**：
- **一度だけ取得**：動作を検証しやすいが、インデックスの構築・保存・同期が必要
- **複数ラウンド検索**：基盤と情報の陳腐化がなくなるが、クエリごとにトークンと時間が増える

### コンパクションの適用：何が保持されるかは要約の書き方次第

Claude Codeで `/compact` を使用する場合、要約に何を含めるかはツールが決定します。APIでは、手動で要約用プロンプトを書くことになります。

| 要約用プロンプトの質 | 結果 |
| :--- | :--- |
| 「これまでの会話を要約してください」 | 重要な状態が失われる可能性がある |
| 「変更されたすべてのファイルパス、下されたすべての判断、発生したすべてのエラーとその解決方法を保持したまま、会話を要約してください」 | タスク上重要な状態を保持できる |

> **要約の指定が不十分なことによるタスク上重要な状態の欠落は、複数セッションにわたるエージェントの失敗の中でも最もよくある原因の1つです。**

---

### サブエージェントへの引き渡し：長期にわたるタスクの管理

タスクが1つのコンテキストウィンドウに収まらないほど大きい場合、ウィンドウを大きくすることは解決策にはなりません。解決策は、**タスクを分解し、関連するコンテキストだけを各サブエージェントに渡すこと**です。

サブエージェントが受け取るもの：
- 範囲を絞ったタスクと、それに必要な最小限のコンテキスト
- 直接関係する前段のステップの結果
- タスクを完了するために必要なツール
- 明確な終了条件

親エージェントがその結果を集約します。コンパクションやプルーニングと同様、サブエージェントへの引き渡しには実装上の負担が伴うため、**コンテキストのコストが実際に制約となる場面でのみ適用**してください。

---

### まとめ

| 分類 | 内容 |
| :--- | :--- |
| **うまく対応できる** | トークン予算を超え、分解が必要な複数ステップのエージェントセッション。本番環境での対処として後付けするよりも、設計段階で組み込むのが最善。 |
| **別の手法を使う** | ウィンドウの上限に近づくことのないパイプライン。管理のための負担を追加する前に、実際のトークン使用量をモデルのコンテキスト上限と比較して測定してください。 |

## 画面2：注意点（5分）
### 開発環境では問題なく動いたのに、本番環境で上限に達したセッション

#### 状況設定

ツールの出力は、プロンプトやファイルの読み込みと同じように、コンテキストを消費します。ツールの出力が短い場合、各ターンがその累計にわずかしか加わらないため、予算は長く持ちます。ツールの出力が大きくなると、各ターンが同じ累計に多く加わるため、予算はより早く尽きます。

> **ウィンドウ自体が変わったわけではなく、変わったのは、各ターンがそのうちどれだけを消費するかです。**

#### 事後分析：本番環境のツール出力に対してコンテキスト予算を測定していなかった事例

あるエージェントが、**4万トークンのコンテキストウィンドウ予算**の下で、販売レシートを処理するために構築されました（この上限はモデルの限界ではなく、チームがコスト管理として設定した予算）。

| 環境 | 平均ツール出力 | ウィンドウが満杯になるまでのターン数 | 観察された症状 |
| :--- | :--- | :--- | :--- |
| **開発環境** | 1回あたり約800トークン | 上限に達することなくセッション完了 | なし |
| **本番環境** | 1回あたり約3,200トークン | 8ターン目で上限に到達 | 8ターン目から、誤ったツール選択と不完全な出力が発生 |

本番環境では、レシートに取引記録やや り取りの記録などの補足資料が含まれていました。ツールの出力だけで8ターン分で約25,600トークンに達し、さらにシステムプロンプト、ユーザーメッセージ、アシスタントメッセージを加えると、累計が4万トークンの予算上限に達しました。

エージェントが誤ったツールを選び始めた理由：積み重なったツール出力によって、**システムプロンプトと初期の指示が押し出されてしまい**、エージェントは最初に持っていた指針を含まないコンテキストウィンドウの上で判断を下すことになっていました。

修正：使用後にツール出力を整理し、上限に達する前に事前にコンパクションを適用する。

#### 教訓

> - **開発時のテスト用データは、本番環境のデータよりも短い**（ほぼすべてのエージェントに当てはまる）
> - 修正策：エージェントを公開する前に、**対象とするデータの中で見つけられる最大の入力に対して、ツール結果の実際のトークンコストを測定する**
> - コンテキストの溢れは**ツール選択の失敗**のように見える。一定数のターンを過ぎたあたりでツール選択が劣化するのを見た場合は、スキーマのデバッグを始める前に、**コンテキストウィンドウが満杯になっていないかを確認**してください

## 画面3：チェックポイント（3分）
### コンテキストの不具合を診断する

以下のセッショントレースは、ツール選択が徐々に劣化していく、複数ターンにわたるエージェントの実行を示しています。

#### セッショントレース

| ターン | 呼び出されたツール | 結果のサイズ |
| :--- | :--- | :--- |
| 1 | `fetch_policy_document`、正しい選択 | 2,400トークン |
| 2 | `fetch_policy_document`、正しい選択 | 2,400トークン |
| 3 | `fetch_policy_document`、正しい選択 | 2,400トークン |
| 4 | `fetch_policy_document`、正しい選択 | 2,400トークン |
| 5 | `apply_coverage_rule` の代わりに `search_knowledge_base`、**誤った選択** | 1,800トークン |
| 6 | 再び `search_knowledge_base`、**誤った選択**（5ターン目と同じ） | 1,800トークン |
| 7 | 結果を得られずセッション終了 | — |

> **Turn 4 の状態**：4件の大きなツール結果（9,600トークン）がコンテキストウィンドウを占めており、次にどのツールを使うべきかをClaudeに伝える指示を圧迫しています。

#### 選択肢
- **A**：`apply_coverage_rule` のツールスキーマに、より明確な説明を追加します。
- **B**：積み重なった出力が現在の指示を押し出さないように、各ターンの後に `fetch_policy_document` の結果を整理し、5ターン目の前にコンパクションを適用します。
- **C**：APIの呼び出しで `max_tokens` を増やし、Claudeが応答できる余地を増やす。

#### 正解と解説

**正解：選択肢B**

失敗は1ターン目ではなく**5ターン目**で発生しました。1〜4ターン目で正しいツール選択がされていることから、スキーマの説明の問題は排除されます。5ターン目でのずれは、積み重なったコンテキストを示しています。そこには4件の大きなツール結果が含まれており、ウィンドウを満たし、現在の指示を端へ押し出していました。
