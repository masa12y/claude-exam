# プロンプティングの技法

- 画面数：3画面（教育20分、注意点5分、チェックポイント4分）

---

## 画面1：教育（20分）
### システムプロンプト、XML、フューショット、出力制約

対話的な利用で一度うまく動いたプロンプトも、本番環境で未検証の入力に対して実行すると、しばしば破綻します。この問題の解決策は、単に言葉を増やすことではなく、プロンプトに欠けている構造上の要素を見極め、その1つを追加することです。このセクションでは、失敗した出力の読み方を確認し、その修正につながる4つの技法を順に見ていきます。

---

### Claudeの出力形式を安定させる4つの技法

初回の応答が期待に届かないとき、つい、プロンプトに言葉を追加して再実行したくなります。しかし、その反応はむしろ問題の切り分けを難しくし、解決につながることはほとんどありません。言葉を言い換えても、表現が変わるだけで、プロンプトに欠けている構造上の要素を補うことにはなりません。

例えば、Claudeが指示と入力データの境界を越えてしまっている場合、表現を明確にするだけでは解決しません。また、出力形式がぶれ続けている場合、「正しい形式で出力してください」と付け加えても解決しません。

失敗のパターンを見れば、4つの技法のうちどれが欠けているかが分かります。まずプロンプトがどのように失敗しているかを診断し、その失敗に対応する特定の技法を追加してください。

#### 失敗診断の表

| 観察された現象 | プロンプトに欠けているもの | なぜこの技法が解決策になるのか |
| :--- | :--- | :--- |
| **結果が誤った形式で返ってくる**<br>（ラベルを期待していたのに文章が返る、JSONを期待していたのに地の文が返る、等） | **出力制約**<br>プロンプトが応答の形式、フィールド名、終了位置を一度も指定していない。 | 出力制約は、応答の内容とは無関係にその形式を制御します。これがなければ、Claudeは一見妥当なテキストを返しますが、後続のパーサーはそれを受け付けるように作られていません。 |
| **内容がずれている**<br>（範囲が広がる、トーンが変わる、あるいは尋ねた以上の広い質問に答えてしまう。会話が進むほど悪化する） | **システムプロンプト**（またはより具体的なシステムプロンプト）<br>振る舞いに関する取り決めが曖昧すぎて、複数ターンにわたって維持できていない。 | システムプロンプトは、どのユーザーターンであっても適用されるルールを定めます。それが十分に規定されていないと、会話が進む中で役割・範囲・形式を一定に保つものが何もなくなります。 |
| **タスク自体は正しいが、構造が独自に作られている**<br>（Claudeはやるべきことを理解した上で、依頼していない形式の出力を生成している） | **フューショットの例**<br>Claudeは説明だけから正確な構造を推測することはできません。 | フューショットの例は、パターンを説明するのではなく、実際に示します。正しい入出力の組を1つ示すだけで、Claudeが合わせるべき正確な形式が伝わりますが、文章による指示だけではそれをうまく特定できないことが多くあります。 |
| **検証した入力に対しては出力が整っているが、想定外のパターンでは破綻する**<br>（エッジケース、通常と異なるフィールド、想定していなかった入力など） | **想定外のパターンをカバーする制約**<br>典型的な流れには対応していますが、パーサーが破綻するケースに対応するルールがありません。 | プロンプトは狭い範囲の入力に対してのみ検証されていました。想定外のパターンを制約の中で明示するか、それをカバーする例を追加することで、テスト用の入力では見えていなかったギャップを塞ぐことができます。 |

### 実例：分類プロンプトの改善前と改善後

サポートチケットを「`billing`（請求）」「`technical`（技術）」「`escalation`（エスカレーション）」の3つのカテゴリーにClaudeで分類する例です。

#### 改善前（素の指示）
```text
System: "You are a support classifier. Classify the ticket."

User: <ticket>I was charged twice for the same month.</ticket>
```
- **現象**：Claudeはあるときは「Billing」、別のときは「billing」、さらに時には「これは請求の問題のようです」といった完全な文章を返す。後続のルーターは固定ラベルを期待しているため、この不整合で失敗する。
- **診断**：表の1行目に該当。出力制約が欠けている。

#### 改善後（3つの技法を適用）
```text
System: "You are a support classifier. Classify each ticket into exactly one of: BILLING, TECHNICAL, ESCALATION. Return only the label. No other text."

<sample_input>My account shows two charges for April.</sample_input>
<ideal_output>BILLING</ideal_output>

<sample_input>The API keeps returning a 429 error.</sample_input>
<ideal_output>TECHNICAL</ideal_output>

User: <ticket>I was charged twice for the same month.</ticket>
```

#### 各技法の役割
1. **システムプロンプト**：出力の取り決めを定義（「固定された集合からちょうど1つのラベルのみを返す」「他のテキストは返さない」）。
2. **XMLタグ**：各例の境界を示し、Claudeが例を指示の一部として誤読することを防ぐ。
3. **フューショットの例**：正確な大文字・小文字の使い方（`BILLING`）と形式を実際に提示。

#### 技法適用の指針
- **4つの技法をすべて組み合わせる**：明確に定義された出力の取り決めに対して組み合わせる。形式が十分に規定されており、例でカバーできるエッジケースを持つタスク。
- **プロンプトを簡略化する**：1つの技法しか必要としない単純なタスク（例：「この段落を要約してください」）に4つすべてを追加しない。
- **追加する前に診断する**：反復するたびにただ長くなっていくプロンプトは危険。5回再プロンプトしてもうまくいかない場合は、文章を追加する前に失敗の種類を診断する。

---

### 各技法をいつ使うべきか

- **システムプロンプト**：セッション全体にわたる振る舞いの取り決めを担う。一度書いたら永続的な指示の層として扱い、Claudeの役割、出力形式、会話間で変わってはならないルールを定義する。
- **XMLタグ**：プロンプト内の異なるコンポーネント（指示、例、入力データ、コンテキスト）を明確に分離する。
- **フューショットの例**：言葉での説明が難しい正確な形式やニュアンスを、入出力の具体例で直接示す。
- **出力制約**：許容される形式、フィールド、値の候補、終了ルールを厳格に指定する。

---

### 構造化出力（Structured Outputs）：出力の制御をプロンプトからAPIへ移す

プロンプトへの指示はあくまで「依頼」であり、モデルが余計な一文や不正なJSONを返してしまうリスクがあります。
Claude APIの**構造化出力**は、言葉で形式を依頼する代わりにJSONスキーマを渡し、**制約付きデコーディング（constrained decoding）**によってスキーマに一致する出力のみをトークン単位で強制する仕組みです。

#### 2つの構造化出力方式

1. **JSON出力（output_config.format）**
   - **用途**：最終的な応答テキスト自体を制約する。`output_config.format` に `type: "json_schema"` とスキーマを指定する。
   - **活用場面**：サポートチケットからのフィールド抽出やAPIレスポンス整形など、モデル自身が構造化ペイロードを生成する場面。パースとリトライのコードが不要になる。
2. **厳格なツールユース（Strict Tool Use）**
   - **用途**：Claudeがツールに渡す引数を制約する。ツール定義で `strict: true` を設定する。
   - **活用場面**：不正な引数が関数クラッシュや誤動作を引き起こすエージェンティックループ。

#### 構造化出力の導入コストと検討事項

- **初回のレイテンシ増加**：スキーマを文法（グラマー）へとコンパイルするため初回呼び出しが遅くなる。コンパイル済み文法は最後に使用してから**24時間キャッシュ**される。スキーマを頻繁に変更するワークロードでは繰り返しコストが発生する。
- **入力トークン数の増加**：APIが期待される形式を記述したシステムプロンプトを自動追加するため、入力トークン数がわずかに増加する。
- **スキーマ保証 ≠ 成功保証**：
  - **拒否（Refusal）**：安全性の理由から拒否された場合、`stop_reason: "refusal"` が付与される。
  - **切り捨て（Truncation）**：`max_tokens` の上限に達して構造の途中で停止した場合、`stop_reason: "max_tokens"` となる。
  - コード側で必ず `stop_reason` を確認する必要がある。
- **メッセージのプリフィル（prefill）とは併用不可**：JSON出力とアシスタントメッセージのプリフィルは同時に使用できない。

## 画面2：注意点（5分）
### 長くなるほど改善するわけではなかったプロンプト

#### 状況設定
プロンプトが本番運用の準備が整っているように見えても、目立たない失敗を引き起こすことがあります。エッジケースによってフィールドが欠落したり制約が無視されたりするのは、多くの場合、制約が十分に精密に指定されていなかったためです。

#### 6回の修正トレース

| 回 | 追加した内容 | 出力の挙動 |
| :---: | :--- | :--- |
| **1** | 「このチケットをbilling、technical、escalationのいずれかに分類してください。」 | 完全な文章が返ってくる（「これは請求の問題のようです。」）→ **パーサーが失敗** |
| **2** | 「簡潔に。」と「カテゴリー名のみを使用してください。」を追加。 | あるときは大文字の「Billing」、別のときは小文字の「billing」が返る → **大文字・小文字の不一致でルーターが失敗** |
| **3** | 各カテゴリーを詳しく説明する3つの段落を追加。 | 単純なチケットでは正しい。曖昧なチケットでは単一ラベルではなく「billing/technical」を返す → **スラッシュでパーサーが失敗** |
| **4** | 「2つのカテゴリーを返さないでください。」と「曖昧な場合は最も可能性の高いものを選んでください。」を追加。 | チケットの80%では機能。2つに当てはまり得るチケットで失敗し、ラベルではなく完全な説明文が返る。 |
| **5** | エッジケースについての段落をさらに2つと、精密さを求める注意書きを追加。 | **冗長なプロンプトが冗長な出力を生む**ようになり、1回の呼び出しで2,000文字を超過。モデルは入力に合わせて応答の長さ・スタイルを調整するため、レイテンシが大幅増加し、精度は改善せず。 |
| **6** | すべての指示をJSONスキーマと、正確な入出力の組を示すフューショットの例2つに置き換えた。 | すべてのチケットで `{"category": "billing"}` が返る。パーサー正常、レイテンシ低下、曖昧チケットの精度も良好。 |

#### 2つの失敗の見極め
1. **4回目の失敗＝診断の失敗**：制約ではなく説明を追加してしまったため、出力が破綻し続けた。
2. **5回目の失敗＝エンジニアリングの失敗**：プロンプトが冗長になりすぎてレイテンシの悪化を招いた。モデルは入力の長さに合わせて出力を調整する性質がある。

> **教訓：** 修正はわずか2行です。正確な形式を指定する**出力制約**と、曖昧なケースをカバーする**フューショットの例2つ**です。3回連続で再プロンプトしてもうまくいかない場合は、文章の追加をやめて、欠けている技法を診断してください。

## 画面3：チェックポイント（4分）
### 壊れたプロンプトを修正する

#### 問題
サポートチケットから、`category`（カテゴリー）、`urgency`（緊急度）、1文の要約（`summary`）という3つのフィールドを持つJSONオブジェクトを抽出します。このプロンプトの欠陥を修正した正しいシステムプロンプトを作成してください。

**壊れたプロンプト：**
```text
System: "You are a support ticket processor. Extract the key information from the ticket below."

User: <ticket>My API key stopped working after I rotated it last night. I have a production deployment that is failing. This needs to be fixed immediately.</ticket>
```

#### 模範解答
```text
System: "You are a support ticket processor. Extract the key information from each ticket and return only a JSON object with exactly these three fields: category (one of: billing, technical, escalation), urgency (one of: low, medium, high, critical), and summary (a single sentence describing the issue). Return only the JSON object. No other text."

User: <ticket>My API key stopped working after I rotated it last night. I have a production deployment that is failing. This needs to be fixed immediately.</ticket>
```

**期待される出力：**
```json
{
  "category": "technical",
  "urgency": "critical",
  "summary": "Developer's API key stopped working after rotation, causing a production deployment failure that needs immediate resolution."
}
```

#### 解説
欠陥は**出力制約が欠けていたこと**でした。元のシステムプロンプトは、JSONの構造、正確なフィールド名、許容される値、他に何も返さないという指示のいずれも指定していませんでした。その取り決めがなければ、Claudeは一見妥当だが一貫性のない出力を返し、パーサーを破壊してしまいます。
