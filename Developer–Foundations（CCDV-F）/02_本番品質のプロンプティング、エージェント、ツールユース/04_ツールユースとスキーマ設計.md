# ツールユースとスキーマ設計

- 画面数：3画面（教育20分、注意点5分、チェックポイント後述）

## 画面1：教育（20分）
### Claudeが正しく選択できるツールスキーマ：定義、ループ、呼び出しパターン

プロンプティングの技法はClaudeが何を生成するかを形作るものでしたが、ツールユースでは、Claudeに一連の行動を渡し、その中から正しいものを選ぶことを託します。その選択は、ほぼすべてスキーマに書いた内容によって決まります。

---

### ツールユースのループはどのように機能するか

> **よくある誤解：** Claude自身がツールを実行しているという考え

**実際の仕組み：**
1. Claudeはツール定義を読み、状況に合ったものを判断する
2. 必要な入力引数とともに「何を呼び出すべきか」をアプリケーションに伝える
3. **アプリケーション側がツールを実行**し、結果を取得して返す
4. Claudeはその結果を使って処理を続ける

**重要：** Claudeが担う部分とコードが担う部分の境界こそ、ツールユースの不具合の大半が発生する場所です。アプリケーションが返却を正しく処理しないと、Claudeは要求したデータを受け取れず、ループが破綻します。

#### ツールユース実装の6つの手順（ループは自動では進まない）
1. **スキーマを定義する**：名前、説明、入力スキーマを持つ定義を作成
2. **メッセージを送信する**：ツール定義を含めてClaudeにリクエスト
3. **`tool_use` ブロックを受け取る**：Claudeがツール呼び出しを決定
4. **ツールを実行する**（コード側の担当）：アプリケーションが実際のAPIや関数を実行
5. **結果を返す**：`tool_result` ブロックとしてClaudeに送信
6. **Claudeが処理を続ける**：結果を踏まえて次の応答または追加のツール呼び出しを生成

失敗が系統的に起きる場合、修正すべきは「1. スキーマ定義」のステップです。

---

### ツールユースの会話におけるメッセージブロックの構造

ツールユースの会話はプレーンテキストではなく、**構造化されたブロック**から構成されます。

#### 4種類のメッセージブロック

| ブロックタイプ | 役割（送信者） | 内容 | 重要なルール |
| :--- | :--- | :--- | :--- |
| **`text` ブロック** | アシスタント／Claude | Claudeによる文章の出力 | Claudeは同じターンの中で `tool_use` ブロックと並んで `text` ブロックを返すことがあります。コードはそのターンを会話履歴に追加する際、**`text` ブロックを含む `content` 配列全体をそのまま保持**する必要があります。取り除くと、後続ターンで依拠するコンテキストが壊れます。 |
| **`tool_use` ブロック** | アシスタント／Claude | ツール名、一意のID（`id`）、入力引数（`input`） | すべての `tool_use` ブロックは、**直後に続くユーザーのターンで `tool_result` ブロックによって応答**されなければなりません。対応関係がないとAPIはリクエストを拒否します。 |
| **`tool_result` ブロック** | ユーザー（アプリ） | 対応する `tool_use_id`、結果内容（`content`）、任意の `is_error` フラグ | `tool_use_id` の値は元の `tool_use` ブロックと完全に一致する必要があります。ClaudeはこのIDで呼び出しと結果を結び付けます（並列呼び出しで結果の順序が変わる場合に特に重要）。 |
| **`thinking` ブロック** | アシスタント／Claude | Claudeの内部推論（拡張思考有効時のみ） | 以降のターンで**変更せずにそのままAPIへ返す**必要があります。署名が壊れるとリクエストが拒否されます。編集済み（`redacted`）ブロックも同様です。 |

> **重要な不変条件：**
> アシスタントのターンにあるすべての `tool_use` ブロックは、**直後に続くユーザーのターンにおいて、同じIDを持つ `tool_result` ブロックで応答されなければならない**。欠落やターンの順序の入れ替わりがあると、API検証エラーが発生します。

### スキーマの構造：Claudeがツール選択の判断のために読む内容

ツールスキーマの3つの要素：
- **`name`（名前）**：具体的で短い識別子にする（例：`get_data` よりも `get_account_balance`）。
- **`description`（説明）**：Claudeが選択を判断するための最も重要な要素。**「使うべき場面」と「使うべきでない場面（除外条件）」の両方を記述する**。
  - ❌ 悪い例：「情報を探すために使用してください」（他の検索・取得ツールと区別できない）
  - ⭕ 良い例：「特定のアカウントIDの現在の残高を取得するために使用し、取引履歴には使用しないでください」（除外条件が明示的）
- **`input_schema`**：JSON Schemaでパラメータを定義。
  - それがないと呼び出しが成立しないパラメータのみ `required` に指定する。
  - 動作可能なものは `optional` にする。ツール間でパラメータの型が重複していることは誤呼び出しの一般的要因。

---

### スキーマ設計の5つの判断

| 判断事項 | 対処方法 | 重要な理由 |
| :--- | :--- | :--- |
| **サブタスクの依存関係** | あるツールの出力が次のツールの入力になる場合は**逐次実行**（別々のターンとしてモデル化）。独立している場合は**並列呼び出し**を許可。 | 現行モデルは独立した呼び出しを既定で並列化します。依存関係がある場合は最初の結果が得られてから次を組み立てる必要があります。必要に応じて `disable_parallel_tool_use` で1ターン1回に強制可能。 |
| **必須フィールド** | それがないと呼び出しが意味をなさない場合にのみ `required` 配列に含める。 | すべてを `required` にすると、Claudeは根拠のない値を作り出さざるを得なくなります（ハルシネーションの誘発）。 |
| **任意フィールド** | 妥当な既定値があるものや、値がないこと自体に意味があるものは任意とし、コード側で既定値を持たせる。 | 任意フィールドがあれば、推測せずに省略できます。 |
| **説明の長さ** | 各ツールにつき3〜4文程度で、何を行うか、いつ使うべきか、何を返すかを記述。必要なら有効入力の例も含める。 | 短すぎると区別がつかず推測になり、長すぎると判断条件が詳細情報に埋もれてしまいます。 |
| **パラメータの型の重複** | 2つのツールが同じ引数の型を持つ場合、各説明文に対象ドメインや使用条件を明記して区別する。 | Claudeは名前と説明でルーティングし、型は二次的な手がかりにすぎません。説明が似ていると区別不能になります。 |

### 実例：誤ったツール選択を引き起こすスキーマとその修正

`search_knowledge_base` と `get_cached_result` という2つのツールを登録した例：
- **問題**：どちらも「情報を探すために使用してください」で始まっており、曖昧な入力に対して誤ったツールが選ばれる。
- **修正**：それぞれの説明に「除外条件」を追加する。
  ```text
  search_knowledge_base:
  "Use this to search the knowledge base when the user asks a question that requires looking up current information. Do not use this if the result of a prior search in this session already covers the question."

  get_cached_result:
  "Use this to retrieve a result that was already fetched during this session. Only use this if search_knowledge_base was called earlier in this conversation for the same query."
  ```
- **注意**：除外条件による判断は会話履歴全体が渡されていることが前提。過去ターンが切り捨てられると機能しなくなります。

#### ツール設計の指針
- **うまく対応できる**：説明が具体的で除外条件が明示されている場合、確実にルーティングできる。
- **不向きな場面（統合の検討）**：似た処理のツールを区別するために説明を延々と長くしなければならない場合は、**`type` パラメータを持つ1つのツールへ統合**する。

### Model Context Protocol（MCP）の活用指針

ツールの定義・保守・実行をアプリケーション外の標準サーバーに移管するプロトコル。

- **ループ内での位置づけ**：MCPを導入してもClaudeのツールユースループは変わらない。クライアントがMCPサーバーへ `ListToolsRequest` を送り、ツール一覧を受け取ってClaudeに渡す。
- **コンテキストコストの管理**：MCPサーバーは全ツールの定義をコンテキストに追加するため、接続数が多いとメッセージ送信前から予算を圧迫する。
  - **API MCP Connector**（ベータヘッダー `mcp-client-2025-11-20` が必要）：
    - `tools` 配列内の `mcp_toolset` オブジェクトで制御。
    - `defer_loading`（論理値）：モデルが必要とするまで定義の読み込みを遅延。
    - `enabled`（論理値）：サーバー上の個々のツールの有効／無効（許可リスト・拒否リスト）を制御。
- **トランスポート方式**：
  - **stdio**：ローカル実行。Claude DesktopやClaude Codeなどのクライアントが必要。
  - **Streamable HTTP**：リモート接続。クライアント→サーバーはPOST、サーバー→クライアントは任意でGET/SSEストリーム。**Claude APIのMCP Connectorで直接サポートされるのはHTTPサーバーのみ**（従来のSSE専用トランスポートは非推奨）。
- **使い分けの基準**：
  - **MCPを使うべき場面**：GitHubなど、よく保守された公式/サードパーティ製MCPサーバーが存在する場合。
  - **手動スキーマを書くべき場面**：独自ユースケース、またはツールの範囲や説明文の品質を極めて精密に制御したい場合。
  - **両方を組み合わせる場面**：MCPで広範なカバレッジを確保しつつ、`mcp_toolset` の許可リストで絞り込み、重要ツールには精緻な説明調整を行う。

## 画面3：チェックポイント（4分）
### スキーマのバグを見つけて修正する

以下のセッショントレースは、あるエージェントがツールを呼び出し、結果を受け取った後、次のリクエストでAPIの検証エラーが発生する様子を示しています。スキーマは有効であり、ツールの説明も具体的で、ツール結果の内容も正しいものです。

> **事前知識**：`tool_result` ブロックは、その内容が人間によって入力されたものではなくアプリケーションによって生成されたものであっても、常に `user` ロールで送信されます。`role` フィールドが示すのは、そのメッセージをClaudeに送っているのが誰かということであり、内容そのものを作成したのが誰かではありません。

#### セッショントレース

```
Turn 1: User:
  [text]: "What is the current balance for account A-4471?"

Turn 2: Assistant:
  [text]: "I'll look that up."
  [tool_use]: id="toolu_01", name="get_account_balance",
              input={"account_id": "A-4471"}

Turn 3: User (tool result):
  [tool_result]: tool_use_id="toolu_02", content="Balance: $1,240.18"

Turn 4: API response:
  Error: invalid_request_error
  "tool_result block references unknown tool_use_id"
```

#### 選択肢
- **A**：`get_account_balance` の説明を更新し、除外条件を追加します。
- **B**：`tool_result` ブロックの `tool_use_id` を修正し、アシスタントのターンで発行された `id` と一致させます。
- **C**：ツールの `input_schema` に `required` 配列を追加し、`account_id` を省略できないようにします。

#### 正解と解説

**正解：選択肢B**

欠陥は3番目のターン（ユーザーのターン）にあります。アシスタントは `id: toolu_01` を持つ `tool_use` ブロックを発行しましたが、`tool_result` ブロックは `toolu_02` を参照しています。

APIは `tool_use` ブロックと `tool_result` ブロックを**位置ではなく id で対応させる**ため、id が一致しないと、会話の中に存在しない `tool_use` ブロックへの参照として扱われます。

修正後の3番目のターン：

```
Turn 3: User (tool result):
  [tool_result]: tool_use_id="toolu_01", content="Balance: $1,240.18"
```

> **不変条件の再確認**：すべての `tool_use` は、直後に続くユーザーのターンで、**id を正確に保持した**対応する `tool_result` を持つ必要があります。

## 画面2：注意点（5分）
### Claudeを誤ったツールへ導いた説明文

#### 状況設定
スキーマが構文上正しく型テストが通っていても、2つのツールの説明の境界が曖昧な場合、Claudeは本番環境で誤った選択を繰り返します。

#### デバッグセッションのやり取り
```text
デベロッパー：「答えがすでにコンテキストにあるのに、Claudeがsearch_docsを呼び続けてしまいます。」
シニアデベロッパー：「search_docsの説明には何と書かれていますか？」
デベロッパー：「『製品に関する情報を探すために使用してください』とあります。」
シニアデベロッパー：「get_context_summaryには何と書かれていますか？」
デベロッパー：「『現在のセッションから関連情報を取得するために使用してください』とあります。」
シニアデベロッパー：「Claudeの視点では、どちらも『情報を探す』としか言っておらず同じに見えます。どちらか一方ではなく、両方のツールに境界（除外条件）を書く必要があります。」
```

#### 修正方針
- **`search_docs` の説明**：「この会話にまだ存在しない内容を調べる必要がある質問をユーザーがした場合に使用する。**現在のセッションのコンテキスト内に答えがある場合はこれを呼び出さない**」
- **`get_context_summary` の説明**：「**答えが現在のセッションにすでに存在する場合にのみ使用する**。新しい情報を調べるためにこれを使用しない」

#### 教訓
> **使うべき場面を1文、使うべきでない場面（除外条件）を1文。境界が必要なのは一方だけでなく、両方のツールです。**
> 説明を長くしても明確に分離できない場合は、`type` パラメータを持つ1つのツールへの統合を検討してください。
