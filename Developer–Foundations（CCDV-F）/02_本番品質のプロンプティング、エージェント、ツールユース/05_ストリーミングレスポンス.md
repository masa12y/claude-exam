## 画面1：教育（16分）
### レスポンスのストリーミングと、状態を壊さずに部分的な出力を処理する方法

これまでのリクエストはすべて、応答全体が届くのを待ってから処理を行っていました。それでも問題はありませんが、応答が長い場合や、ユーザーが何も表示されない画面を見つめて待っている場合は問題になります。

**ストリーミング**は、モデルが生成するのに合わせて、応答を断片ごとに送信します。これによって処理が速く感じられるようになりますが、コードには新たな役割も生まれます。一連の出力から最終的な内容を自分で組み立てる必要があり、また、その一連の出力が途中で止まった場合にも備えておく必要があります。

---

### ストリーミングによってレスポンスがどう変わるか

| 項目 | ストリーミングなし | ストリーミングあり |
| :--- | :--- | :--- |
| APIの返し方 | すべてのコンテンツブロックが完成した状態の、1つの完全なメッセージ | メッセージが組み立てられていく様子を記述する一連のイベント |
| コードの役割 | そのまま受け取る | 断片を自分で組み立てる |
| 中断への対応 | 不要 | 自分で決める必要あり |

> **重要：** モデルは何らかのライブオブジェクトを開いたまま保持しているわけではありません。各イベントは、1つの変化（ブロックが開始した、テキストや入力がそこに追加された、ブロックが終了した、メッセージ全体が終了した）を記述する、独立した小さなメッセージです。ハンドラーは各イベントを受け取り、それまでに構築してきた部分的な状態へ反映します。

---

### イベントの流れと、それぞれに対してハンドラーが行うこと

| イベント | 示している内容 | ハンドラーが行うこと |
| :--- | :--- | :--- |
| `message_start` | 新しいメッセージが開始することを示す。空の `content` と初期の `usage` を持つ、メッセージの骨格を運ぶ。 | ブロックを収集するための空の `content` 配列を用意する。 |
| `content_block_start` | 新しいコンテンツブロックが開始することを示し、その種類（`text`、`tool_use`、`thinking` のいずれか）と `index` を伴う。 | その `index` に、指定されたブロックタイプ用の枠を作る。`tool_use` ブロックは `name` と `id` を伴って開始するが、この時点では `input` はまだない。 |
| `content_block_delta` | 1つのブロックの断片的な追加分：テキストの断片、ツール呼び出し用JSON入力の断片、あるいはthinkingの断片。 | その断片を、対応する `index` のブロックに追加する。ツール呼び出しの入力は、複数のdeltaにまたがる部分的なJSON文字列として届くため、ブロックが閉じるまでパースすることはできない。 |
| `content_block_stop` | このindexのブロックが完了したことを示す。 | ブロックを確定させる。`tool_use` ブロックの場合、この時点で初めて、積み重ねてきたJSON入力がパースできるだけの完成度に達する。 |
| `message_delta` | メッセージ全体レベルの変化：`stop_reason` と最終的な `usage` の集計。 | `stop_reason` を記録する。これは、モデルが完了したのか、それとも他の理由で停止したのかを示す。 |
| `message_stop` | ストリームが完了したことを示す。 | 組み立てられた `content` 配列が、完成したメッセージとなる。この時点から先は、ストリーミングを使わないレスポンスと完全に同じように扱う。 |

---

### 状態を壊さないためのルール：不完全なブロックに対して処理を行わない

`tool_use` ブロックに注意してください。その `input` は、多数の `content_block_delta` イベントにまたがる部分的なJSON文字列として現れ、`content_block_stop` がそのブロックを閉じるまで有効なJSONにはなりません。

ブロックが閉じる前にコードがその `input` をパースしたりツールを実行しようとしたりすると、不正な形式のJSONで失敗するか、引数が半分欠けた状態で実行されてしまいます。

> **ルール：** deltaを集め、そのブロックの `content_block_stop` が届いた後にのみ処理を行ってください。

同じ心がけは、ストリーミングされたアシスタントのターンを会話履歴に追加する際にも当てはまります。すべてのブロックが完全に組み立てられた後、`message_stop` が届いてから追加してください。途中で中断したストリームから構築されたターンは不完全であり、半端に組み立てられた `tool_use` ブロックが履歴に残っていると、次のリクエストが拒否されます。

---

### ストリームが途中で止まった場合

ストリームが途中で失敗することもあります（ネットワーク接続の切断、タイムアウト、クライアントの切断など）。

| 対処方針 | 内容 |
| :--- | :--- |
| **完了を意図的に追跡する** | ターンは、`message_stop` が届いた時点でのみ利用可能になる。それまでは暫定的なものとして扱う。 |
| **中断時は破棄して再試行** | 不完全なアシスタントのターンを履歴に保存せずに破棄し、リクエストを再試行する。半端に組み立てられたターンを確定させることが、次のリクエストを壊す原因になる。 |
| **`stop_reason` を確認する** | ループを続ける前に、`message_delta` から `stop_reason` を確認する。`tool_use` であればツール実行準備完了、それ以外は別の経路。 |

---

### ストリーミングの使いどころ

| 分類 | 内容 |
| :--- | :--- |
| **うまく対応できる** | 長い応答や、生成されるとともに出力を表示することで待ち時間をなくせる、ユーザー向けのインターフェース。 |
| **複雑さやコストが増す** | ブロックを自分で組み立てる必要があり、不完全なブロックに対して処理を行ってはならず、ストリームの途中での中断にも明示的に対応する必要があります。 |
| **別の手法を使う** | 短い応答や、誰も出力を待っていないバックエンドの処理では、ストリーミングを使わない呼び出しの方が単純であり、不完全な状態のリスクを完全に排除できます。 |

## 画面2：注意点（5分）
### 履歴に書き途中のツール呼び出しを残したストリーム

#### 状況設定

ストリーミングされた応答は画面上では問題なく見えても、次のリクエストを壊してしまうことがあります。テキストは表示され、ユーザーには答えが見え、ハンドラーはそのターンを履歴に追加しました。ハンドラーが検知できなかったのは、ストリームがブロックの途中で切断されたことでした。そのため、保存された `tool_use` 呼び出しは、`input` が半分欠けたものになっていました。次のリクエストは検証に失敗し、エラーは原因となったストリームではなく、次のターンを指し示します。

#### 事後分析：ストリームの切断後、不完全な tool_use ブロックが履歴に確定してしまった事例

あるエージェントは、オペレーターが応答の生成をリアルタイムで見られるように、ストリーミングを使用していました。ハンドラーは `content_block_delta` イベントを積み重ね、**読み取りループが終了した時点**でアシスタントのターンを履歴に追加していました。

高速なローカル接続でのテストでは、ストリームは常に最後まで完了していたため、ループは常に `message_stop` で終了し、保存されるターンは常に完全なものでした。

本番環境では、あるストリームが、`tool_use` ブロックが開始し、JSON入力の一部を受け取った後、`content_block_stop` の前にネットワークの不具合で終了しました。読み取りループはいつもと同じように終了したため、ハンドラーはそのターンを追加しました。それは、**input文字列が途中で切れたJSONになっている `tool_use` ブロック**を含む、アシスタントのターンでした。

オペレーターは不完全な答えを見て、再試行しました。その再試行のリクエストには、履歴の中にその壊れたターンが含まれており、APIは不正な形式の `tool_use` ブロックを指し示す検証エラーとともにそれを拒否しました。

エラーが再試行のリクエストで表面化したため、チームは半日をかけてスキーマと再試行のロジックを調査しました。しかし、実際の原因はそれより前の段階にありました：ハンドラーが「**読み取りループが終了した**」ことを「**メッセージが完成した**」ことと同じものとして扱っていました。この2つは同じではありません。

#### 教訓

> **ストリームの終了は、メッセージの完成と同じではありません。**
> メッセージが完全であることを意味するのは、`message_stop` のみです。
> 
> - 履歴への追加は `message_stop` が届くまで待つ
> - 中断が起きた場合は不完全なターンを破棄し、最後に完了したターンから再試行する
> - 再試行時にツールユースのエラーが表れた場合は、スキーマに手を加える前に、**直前のターンがストリームから組み立てられたものかどうか**を確認する

## 画面3：チェックポイント（4分）
### 壊れたストリームハンドラーを修復する

以下のハンドラーは、応答をストリーミングし、アシスタントのターンを会話履歴に追加します。このハンドラーには、ストリームが中断された場合にのみ表面化する欠陥が1つあります。その欠陥を特定し、修正版を書いてください。

#### 壊れたハンドラー

```python
blocks = {}
stop_seen = False
with client.messages.stream(model=model, max_tokens=4096, messages=messages, tools=tools) as stream:
    for event in stream:
        if event.type == "content_block_start":
            blocks[event.index] = init_block(event)
        elif event.type == "content_block_delta":
            apply_delta(blocks[event.index], event.delta)
        elif event.type == "message_stop":
            stop_seen = True
messages.append({"role": "assistant", "content": assemble(blocks)})
```

#### 欠陥

`message_stop` が届いたかどうかにかかわらず、追加処理が実行されてしまいます。ストリームが中断すると、半端に組み立てられた `tool_use` ブロックを含む可能性がある不完全なターンが、そのまま履歴にコミットされてしまいます。

#### 模範解答

```python
blocks = {}
stop_seen = False
with client.messages.stream(model=model, max_tokens=4096, messages=messages, tools=tools) as stream:
    for event in stream:
        if event.type == "content_block_start":
            blocks[event.index] = init_block(event)
        elif event.type == "content_block_delta":
            apply_delta(blocks[event.index], event.delta)
        elif event.type == "message_stop":
            stop_seen = True
if stop_seen:
    messages.append({"role": "assistant", "content": assemble(blocks)})
else:
    raise StreamInterruptedError(
        "Stream ended before message_stop; discarding partial turn. Retry from the last complete turn."
    )
```

追加処理を `stop_seen` で制御することで、完全なメッセージのみが履歴に入るようになります。ストリームが中断した場合に例外を発生させることで、不正な形式のブロックでコンテキストを壊すのではなく、最後に完了したターンからリクエストを再試行できるようになります。
