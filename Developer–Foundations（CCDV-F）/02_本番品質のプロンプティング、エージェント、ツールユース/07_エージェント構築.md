## 画面1：教育（22分）
### 本番環境向けエージェントの構築：ループ、配線パス、オーケストレーション、ヒューマン・イン・ザ・ループ

エージェントとは、コンテキストを管理し、明確な目標を持った、複数ステップのツールユースのループです。

各要素が複数のターンにわたって一緒に動くようになると、個別のテストでは捉えられない新しい失敗パターンが現れます：
- 単一ターンのテストではうまく機能していたルーティングの判断が、積み重なっていく
- コンテキストは想定よりも早く満杯になる
- 以前の結果に依存するステップが、前のツール呼び出しの構成が誤っていたために、誤った入力を受け取ってしまう

> **最初に問うべき問い：この問題にエージェントが本当に必要なのか**
> エージェントには、より単純なパターンと比べて、調整のための負担、拡大するコンテキストのコスト、失敗が起こりうる範囲の広さが伴います。

---

### ワークフローかエージェントか：最初の1行を書く前に決める

エージェント開発における最も重大な誤りは、最初に誤ったパターンを選んでしまうことです。

| ワークフローを選ぶべき場面 | エージェントを選ぶべき場面 |
| :--- | :--- |
| 正確なステップをコードとして列挙できる | 目標とツールは指定できるが、正確な経路は指定できない |
| エラーのコストが実際に大きく、ステップ単位のガードレールが重要 | 作業を進める経路を事前に列挙できない |
| 標準的なツールによるオブザーバビリティが必要 | 再現性のなさ（非決定性）が許容され、エージェントが取り得る行動が登録されたツールセットによって制約されている |
| 入力が既知の集合に十分に制約されている | ユーザーの入力が、内容と構造の両面で予測できないほど変化する |
| タスクの実行が毎回同じ順序で進む | タスクに、利用可能なツールを創造的に組み合わせる順序付けが必要 |

> **エージェントとはパターンである。配線パスは実装上の選択である。**

### 配線パス：誰がループを実行し、何を自分が担うのか

3つのパスは、エージェントの実行環境をどれだけ自分で持つかという点で異なります。

| 配線パス | 誰がループを実行するか | 自分が担うもの | 選ぶべき場面 |
| :--- | :--- | :--- | :--- |
| **Messages APIに対して直接ループを書く** | すべての反復を自分のコードが実行。リクエストを送信し、`tool_use` ブロックを読み取り、ツールを実行し、結果を自分で追加する。 | ループ全体、ツールの実行、コンテキスト管理、再試行、終了条件。何も用意されていない。 | 各ステップを完全に制御する必要がある場合、ライブラリでは対応できない制約がある場合、またはループの仕組みを自分で学びたい場合。 |
| **Agent SDK** | 同じループを自分のプロセスの中で実行し、ツールの実行・コンテキスト管理・反復の構造をすでに組み込んだ形で提供する。 | ツールの実行は依然として自分のコードが担う。 | プロセス内での制御が必要で、基盤の構築コストを減らしたい場合。 |
| **Claude Managed Agents**（現在パブリックベータ版） | Anthropicがループとサンドボックスを実行。アプリケーションはイベントを送信して結果をSSE経由でストリーミングとして受け取る。 | エージェント定義（バージョン管理されたAPIリソースとして）とアプリケーション層。ループ、サンドボックス、ツール実行ランタイムは担わない。 | タスクが長時間にわたる場合、またはサンドボックスやループを自分で構築・保護したくない場合。 |

#### Claude Managed Agents：使いどころと制約

**適した場面：**
- タスクが分単位・時間単位の長時間実行
- マネージド型のサンドボックスを使いたい
- ループ・サンドボックス・ツール実行の層を一切自分で構築したくない

**決定的な制約：**
Managed Agentのセッションはステートフルであり、サーバー側に保存されます。そのため、現時点でこれらのセッションは**Zero Data Retention（ZDR）やHIPAAのBusiness Associate Agreement（BAA）の対象にならない**ことに注意が必要です。PHIが含まれる場合やZDRの要件が適用される場合は、**Agent SDKまたは素のループ**を使うことになります。

### ループの配線：どのパスでも変わらない4つのステップ

| ステップ | 内容 | 注意点 |
| :--- | :--- | :--- |
| **1. ツールを登録する** | 各ツールは同じスキーマ構造に従い、SDKがそれらをエージェントに対して登録する | 未登録のツールがシステムプロンプトで参照されていないことを確認する |
| **2. システムプロンプトを設定する** | エージェントのタスクに合わせて範囲を絞る | 広範なシステムプロンプトは、より広く信頼性の低いツールルーティングを生む |
| **3. ツールユースのループを処理する** | Claudeが発行するすべてのツール呼び出しを、コードが実行してtool_resultとして返す | 1つのアシスタントのターンにある複数の `tool_use` ブロックは、まとめて解決される必要がある |
| **4. 終了条件を定義する** | 明確な停止基準を定義する | Claudeが自主的に停止することに依存しないこと |

---

### ループ配線のチェックリスト

| # | 項目 | 確認すべきこと |
| :--- | :--- | :--- |
| 1 | **ツールが登録されている** | エージェントが必要とする可能性のあるすべてのツールが登録リストに含まれている。システムプロンプトの中で、未登録のツールが参照されていない。 |
| 2 | **システムプロンプトの範囲が絞られている** | システムプロンプトがタスクと利用可能なツールを明示している。エージェントが持っていないツールについて説明していない。 |
| 3 | **ツールユースのループが実装されている** | コードが、Claudeが発行するすべての `tool_use` ブロックを処理し、次のアシスタントのターンの前に、それぞれに対して `tool_result` ブロックを返している。 |
| 4 | **HITLの挿入位置が定義されている** | ループの中に、少なくとも1箇所のヒューマン・イン・ザ・ループのチェックがある。 |
| 5 | **終了条件が定義されている** | ループには、Claudeが自主的に停止することに依存しない、明確な停止基準がある。 |

### ヒューマン・イン・ザ・ループ（HITL）：挿入位置と、それぞれが適用される場面

> **挿入位置を決める問い：** このステップが人間によるチェックなしに実行された場合、最悪の結果は何か？

| 挿入位置 | チェックが発生する条件 | 対応するリスクレベル |
| :--- | :--- | :--- |
| **破壊的なツール呼び出しの前** | エージェントが、書き込み、削除、送信の操作を実行しようとしている | 高：誤った呼び出しを取り消せない、不可逆な操作 |
| **計画のステップの後** | エージェントが計画を生成し、その実行を始めようとしている | 中：すべてのステップが正しく実行されたとしても、誤った結果を生む可能性のある、不正確な計画 |
| **予期しない出力があった場合** | ツール結果に、エラーフラグ、空の結果、あるいは想定範囲外の値が含まれている | 可変：再試行のロジックだけでは解決しない失敗パターンを捉える |

---

### ツールのオーケストレーション：ツールの過多と過少

エージェントのルーティングの振る舞いは、**ツールがどのように説明されているか**と、**いくつのツールが登録されているか**という2つの要素によって形作られます。

> **本番環境のエージェントでは、ツールの過多の方がより一般的な問題です。**
> タスクに必要な最小限のツールの集合から始め、能力上の具体的な不足が確認された場合にのみツールを追加してください。

### 規制対象データの制約

データを特定の制約（弁護士・依頼者間の秘匿特権、HIPAA、GDPR、FedRAMP、社内のデータ常駐ポリシーなど）の下で扱う必要がある場合、その制約が、**コードがどのエンドポイントを呼び出すか、どの認証情報を持つか、ログがどこに届くか**を決めます。

| 制約 | コード上で除外される傾向にあるもの | コードレビューを通常通過するもの |
| :--- | :--- | :--- |
| **弁護士・依頼者間の秘匿特権** | 法律事務所がエンドツーエンドで監査できない消費者向けデリバリールートからの呼び出し | SSOで認証され、事務所が承認したLLMゲートウェイを経由する直接のAPIまたはSDK呼び出し（アプリケーション層に会話のログ記録を実装し、承認されたログの保存先へ送ること） |
| **HIPAA（PHIの取り扱い）** | BAAの対象になっていないエンドポイントやデリバリールートへPHIを送信するコード | BAAの対象となる構成での直接のAPIまたはSDK呼び出し。AWS BedrockまたはGCP Vertexを経由するクラウド媒介の経路も代替手段として有効。**注：BAAはConsole、Workbench、ベータ機能、消費者向けプランをカバーしない** |
| **GDPRとデータ常駐** | モデルの実行リージョンをコード上で固定できないデリバリールート | クライアント設定で対象となる法域にリージョンを固定した、BedrockやVertexのようなクラウド媒介の経路。**Anthropicの直接のAPIは現時点ではEUのデータ常駐に対応していない** |
| **FedRAMPと政府機関** | 必要なインパクトレベルにおいて承認済みのクラウド環境にないエンドポイントを呼び出すコードパス | Claude for Government（C4G）、Amazon Bedrock GovCloud経由のClaude、Vertex AI Assured Workloads経由のClaude（いずれかを利用。`trust.anthropic.com` で現在の認証状況を確認） |
| **社内のデータ常駐ポリシー** | パートナーの承認済み一覧に含まれないクラウドベンダーに対して設定されたSDKクライアントからの呼び出し | パートナーの承認済みクラウドベンダー上のデリバリールート |

> **統制上の制約を最初に明確にしてください。** 誤ったクライアント設定は、エージェントを配線した後に元に戻すよりも、最初から正しく設定する方がはるかにコストが低い。

## 画面2：注意点（5分）
### 本番ファイルを編集してしまったエージェント

#### 状況設定

このエージェントは、テスト環境が寛容であるためテストでは一貫して機能しますが、本番環境はそうではありません。エージェントは同じツール、同じループ、同じシステムプロンプトを持っていますが、**HITLのチェックポイントが欠けています**。テストでは、それが必要になるようなユースケースが一度も表面化しなかったためです。

#### 事後分析：スクラッチディレクトリでテストされ、顧客環境にデプロイされたファイル編集エージェント

あるデベロッパーが、設定ファイルを読み取り、変更し、書き込むことのできるエージェントを構築しました。システムプロンプトは、`read_file`、`write_file`、`validate_config` という3つのツールへのアクセスを与えていました。

エージェントのループ：
- 書き込みを行うたびに `validate_config` を再実行
- 設定がまだ検証に失敗する場合は、編集を調整して再度書き込みを行う（最大10回の反復）

テストはスクラッチディレクトリに対して実施され、すべてのテストケースで正しく機能し、通常2〜3回の反復で有効な設定に収束していました。

顧客環境にデプロイされたとき、このエージェントは、ある設定パラメータが範囲外であることを正しく特定しました。修正を提案し、`write_file` を呼び出し、`validate_config` を再実行して、合格の結果を得ました。**ループの設計自体は正しかった**のですが、問題は終了条件にありました。

エージェントが修正したパラメータは、顧客のアプリケーションが依存していたレートリミットでした。`validate_config` は、その値がスキーマの許容範囲内にあるかを確認しており、今度はその範囲内に収まっていました。`validate_config` が確認していなかったのは、**後続のシステムがその古い値に依存していたかどうか**でした。書き込みから数分のうちに、顧客のアプリケーションは失敗し始めました。

失敗の原因は、ループの終了条件（`validate_config` が合格を返す）が、エージェントが編集していたファイルの範囲にしか及んでいなかったこと、そして**「このファイルで検証に合格した」ことと「顧客環境への書き込みが確定した」ことの間にチェックポイントがなかった**ことです。

#### 教訓

> **設計時に一度も問われなかった問い：「`write_file` が人間によるチェックなしに実行された場合、最悪の結果は何か」**
> 
> - あるツールが本番環境で不可逆な操作を行える場合、それが実行される前にチェックポイントが必要
> - この制約は、最初の事故が起きた後ではなく、**ツールの範囲を定める設計の段階**で組み込んでおく
> - テストでは使い捨てのスクラッチディレクトリが使われていたため、「誤った書き込み」が触れるものが何も重要ではなく、この隙間は表面化しなかった

#### 模範解答

**空欄1：`update_record` の説明文**

```
"Use this to update a specific field on a customer record. Only call this tool after a read_record call has confirmed the current value and the proposed change has been reviewed. Do not use this for bulk updates or schema changes."
```

この制限的な説明文は、そのツールを呼び出すべきでない場面、呼び出す前に成り立っていなければならない条件、そして絶対に使用すべきでない場面を、モデルがルーティングに使える言葉で伝えています。説明が最小限であれば、エージェントは更新が必要だと推測した時点でいつでも `update_record` を呼び出せてしまい、現在の値を読み取る前や、オペレーターが変更を意図していないフィールドに対しても呼び出してしまう可能性があります。

**空欄2：HITLチェックポイントのコード**


このチェックポイントはループの内部にあり、ツール名で制御を行うため、`read_record` の呼び出しはそのまま通過し、`update_record` の呼び出しは明示的な承認のために一時停止します。

> - `execute_tool` の実行後に承認するのでは、その不可逆な処理はすでに完了してしまっている
