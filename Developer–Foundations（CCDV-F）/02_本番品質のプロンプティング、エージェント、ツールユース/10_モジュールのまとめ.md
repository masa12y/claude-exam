## 画面1：総合 デバッグタスク（8分）
### 各バグを特定する

以下のエージェント実装には、4つの層にそれぞれ1つずつ、意図的に仕込まれた4つのバグがあります。スキーマの層、応答が組み立てられ確定するストリーミングの層、メッセージの構造が構築されるコンテキストの層、メモリーの層です。

#### バグのある実装

```python
# --- TOOL DEFINITIONS ---
tools = [
  {
    "name": "get_customer_data",
    "description": "Gets data.",
    "input_schema": { "type": "object", "properties": { "id": {"type":"string"} }, "required": ["id"] }
  }
]

# --- AGENT LOOP ---
def run_agent(user_request, session_history):
  messages = session_history + [{"role":"user","content":user_request}]
  while True:
    blocks = {}
    stop_seen = False
    with client.messages.stream(
        model=model, max_tokens=4096, tools=tools, messages=messages,
        thinking={"type": "adaptive"}
    ) as stream:
      for event in stream:
        if event.type == "content_block_start":
          blocks[event.index] = init_block(event)
        elif event.type == "content_block_delta":
          apply_delta(blocks[event.index], event.delta)
        elif event.type == "message_stop":
          stop_seen = True
    assistant_content = [b for b in assemble(blocks) if b["type"] != "thinking"]
    messages.append({"role": "assistant", "content": assistant_content})
    response = finalize(blocks)
    if response.stop_reason == "end_turn":
      return response
    for block in response.content:
      if block.type == "tool_use":
        result = execute_tool(block.name, block.input)
        messages.append({"role":"user","content":[{"type":"tool_result",
                         "tool_use_id":block.id,"content":result}]})

# --- MEMORY ---
def build_session_history(prior_sessions):
  # Concatenating all prior session transcripts in-context
  full_history = []
  for session in prior_sessions:
    full_history.extend(session["messages"])
  return full_history
```

#### 課題：ステージ1
上記の実装にある4つのバグについて、それぞれどの層に属するかを明らかにし、実行時に何を引き起こすかを説明してください。

#### 模範解答：ステージ1

- **バグ1（曖昧な説明「Gets data.」）**：**スキーマの層**  
  Claudeはこのツールを他の取得系ツールと区別できず、意図ではなく表面的な一致に基づいて選択してしまいます。
- **バグ2（message_stopの前にターンが確定してしまう。thinkingブロックが取り除かれている）**：**ストリーミングの層**  
  中断されたストリームによって、不完全な（半端に組み立てられた可能性のある）`tool_use` ブロックが履歴に書き込まれます。取り除かれた `thinking` ブロックは持ち越しルールに違反し、署名が一致しなくなるため、APIは次のリクエストを拒否します。
- **バグ3（tool_resultのみが追加されており、その前の完全なアシスタントのtool_useのターンがない）**：**コンテキストの層**  
  APIは、完全なアシスタントのターンとして受け取ったことのない `tool_use` ブロックを参照する `tool_result` を目にし、そのリクエストを拒否します。
- **バグ4（それまでのすべてのセッションの記録がコンテキスト内で連結されている）**：**メモリーの層**  
  コンテキストウィンドウはセッションごとに大きくなり、4回目か5回目のセッションまでに、エージェントが現在のリクエストを処理できるようになる前に満杯になってしまいます。

`thinking` ブロックを含むすべてのブロックを保持します。確定処理を `stop_seen` で制御し、中断時には例外を発生させます。

```python
assistant_content = assemble(blocks)    # thinkingを含むすべてのブロックを保持
if stop_seen:
    messages.append({"role": "assistant", "content": assistant_content})

        "Discarding partial turn; retry from last complete turn."
    )
```

##### バグ4の修正：メモリーの層

```python
def build_session_history(prior_sessions):
```

## 画面3：用語集（3分）
### 本モジュールの重要用語

- **Claude Agent SDK**  
  `@anthropic-ai/claude-agent-sdk`（TypeScript）／`claude-agent-sdk`（Python）として配布される、マネージド型のエージェントランタイムです。これは、Claude Codeを支えているのと同じエージェントループ（反復、ツールの実行、観察、終了）へのプログラムによるアクセスをパートナーに提供します。これにより、パートナーはターミナルでClaude Codeを実行する代わりに、自社のプロダクトの中にエージェントを組み込むことができます。これは、APIに対する薄い便利用のラッパーであり、エージェントループを実行しないAnthropic SDKとは別のものです。
- **コンテキストウィンドウ**  
  モデルが1回のリクエストで処理できるトークンの合計数を指し、システムプロンプト、会話履歴、ツール定義、ツール結果、そしてモデル自身の出力を含みます。累計がその上限に達すると、新しい内容を追加する前に、以前の内容を削除または要約する必要があります。
- **関数シグネチャ**  
  関数シグネチャとは、関数の宣言を指すプログラミング用語です。すなわち、関数の名前と、それが受け取るパラメータの一覧（名前、型、既定値を含む）です。
- **HITL**  
  ヒューマン・イン・ザ・ループ（Human-in-the-loop）とは、重大な結果を伴う操作が実行される前に、自動化されたプロセスの中に人間によるレビューまたは承認のステップを挿入することを指します。
- **リファクタリング**  
  リファクタリングとは、外部から見た振る舞いを変えずに、コードの内部構造を変更することを指します。実装をより整理された、より速い、テストしやすい、あるいは拡張しやすい形にするために再構成、リネーム、書き直しを行いますが、システムの他の部分から見える振る舞いは変わりません。
- **SOC 2**  
  Service Organization Control 2（SOC 2）は、サービス組織が顧客データをどのように取り扱っているかを評価するために、米国公認会計士協会（AICPA）が策定した監査フレームワークです。SaaSベンダーやクラウドサービスプロバイダーが、自社のセキュリティ対策が認知された基準を満たしていることを示すよう求められた際に、最もよく引用される標準です。
- **状態**  
  状態とは、エージェントがターンの間で持ち越す情報を指します。それまでの会話、ユーザーが依頼した内容、以前のツール呼び出しの結果などです。
- **stop_reason**  
  モデルがなぜ生成を停止したのかをコードに伝える、APIレスポンス内のフィールドです。エージェンティックループにおいて最も重要な2つの値は、`end_turn`（Claudeが完了し、それ以上の操作を要求していないことを意味する）と、`tool_use`（Claudeが1つ以上の `tool_use` ブロックを発行し、続行する前に結果を待っていることを意味する）です。
- **サブエージェント**  
  個別のサブタスクを処理するために、オーケストレーションを行うエージェントによって生成される、別のエージェントインスタンスです。サブエージェントは、親セッションから会話履歴、Skills、コンテキストを引き継ぎません。それぞれがクリーンな状態で開始し、必要な指示とツールを明示的に設定する必要があります。結果はオーケストレーターへ返され、オーケストレーターがそれをより大きなタスクの中に組み込みます。
- **トークン**  
  Claudeがテキストを測定し処理するために使用する単位です。トークンあたりの平均文字数は、対象のモデルのトークナイザーに依存し、モデルの世代によって異なります。トークンあたりの文字数に関する目安は、モデルに依存するものとして扱い、実装時に現在のトークナイザーの動作を確認してください。トークンは、プロンプト、応答、ツールスキーマ、ツール結果など、コンテキストウィンドウ内のすべてのものによって消費されます。トークンは、料金とコンテキスト予算の両方の計算の基礎となります。
- **tool_useブロック**  
  Claudeが関数を呼び出したい場合に、アシスタントによって返されるコンテンツブロックです。ツール名、一意のID、そしてClaudeがコードに渡したい入力引数を含みます。すべての `tool_use` ブロックは、直後に続くユーザーのターンで、同じIDを正確に保持した、対応する `tool_result` ブロックによって応答されなければなりません。

## 画面4：振り返り（3分）
### 8つの重要ポイント

1. **プロンプトが失敗したとき、失敗の種類を見ればどの技法が欠けているかが分かる。**  
   誤った形式の出力は出力制約の欠落を示し、ターンをまたいだずれは規定が不十分なシステムプロンプトを示し、ハルシネーションによる構造はフューショットの例の欠如を示します。指示を言い換えて再試行したくなる反応は、ほとんど機能しません。これらの失敗はいずれも言い回しの問題ではないからです。まず失敗の種類を診断し、その後にそれに対応する技法を追加します。未検証の入力がパーサーを壊してしまい、プロンプトレベルの指示では不十分な場合は、構造化出力を使って出力の制御をAPI側へ移します。JSON出力はスキーマに対して最終的な応答を制約し、厳格なツールユースはClaudeがツールに渡す引数を検証します。ただし、最初の呼び出しのコンパイルによるレイテンシと、追加の入力トークンというコストがかかります。
2. **プロンプトを調整する前に、推論の深さをタスクに合わせる。**  
   推論を有効にするのは、推論のパスが答えを変える場合に限り、`effort` 設定は毎回の呼び出しで一律に上げるのではなく、問題に合わせて調整します。シンキングブロックは変更せずにAPIへ返さなければ、次のリクエストが失敗します。どのモデルを実行するかという選択は、推論を有効にするかどうかとは別であり、本モジュールの前に位置するMSO Foundationsモジュールで扱っています。
3. **ストリームの終了は、メッセージの完成ではない。**  
   ストリーミングは、部分的なイベントから自分で応答を組み立てるというコストを払う代わりに、感じられるレイテンシを短縮します。ブロックが閉じた後にのみ処理を行い、`message_stop` が届いた後にのみターンを履歴に確定させ、ストリームが中断した場合は不完全なターンを破棄して再試行します。認識すべき失敗パターンは、再試行時に現れるツールユースのエラーが、スキーマではなく、切断されたストリームによる半端に組み立てられたブロックに起因しているという点です。
4. **誤ったツール選択は必ずスキーマに、そして多くの場合はdescriptionに起因する。**  
   Claudeは `description` フィールドを読み、それをユーザーの依頼と照らし合わせてツールを選びます。つまり、どちらも「情報を探すために使用してください」と書かれた2つのツールは、`input_schema` が全く似ていなくても、Claudeの側からは区別できません。ほとんどの誤ったツール選択の不具合を解決する1文が、除外条件です。それぞれの説明の中に、そのツールを呼び出すべきでない場面を示す一文を、最初の誤った呼び出しがログに現れた後ではなく、設計時にスキーマへ書き込んでおきます。誰かが既にツールを書いている場合、MCPを使えば、すべてのスキーマを自分で作成する代わりに、保守されているサーバーへ接続できます。ただし、接続した各サーバーは、そのツールが実際に使われるかどうかにかかわらず、コンテキストウィンドウにツール定義を追加するため、意図的に接続し、読み込みのコストを管理してください。
5. **コンテキストは固定された予算であり、ツールの出力はループの中で他の何よりも早くそれを消費する。**  
   本番環境のツール出力は、開発で使うテスト用データよりも3〜5倍長くなるため、テストでは50ターンにわたって問題なく持続していたセッションが、公開後には8ターン目で上限に達することがあります。プルーニング、コンパクション、サブエージェントへの引き渡しは、それぞれ異なる形で余裕を取り戻すものであり、どれを適用すべきかは、以前の状態がまだ必要かどうかによって決まります。一定数のターンを過ぎたあたりでツール選択が劣化し始めた場合、最初に確認すべきはスキーマではなくウィンドウです。
6. **ワークフローかエージェントかという判断が、その後のすべてのコストを決め、ヒューマンチェックポイントは設計に組み込むべきものである。**  
   正確なステップをコードとして書ける場合はワークフローが正しい選択であり、目標とツールは指定できるがその間の経路は指定できない場合はエージェントが正しい選択です。どちらの方向であっても、誤った選択は本番環境でしか表面化しません。ワークフローで十分な場面でエージェントを使うと、コンテキストのコストと、トランスクリプトの中にしか残らない振る舞いが増えます。エージェントが必要な場面でワークフローを使うと、入力が想定された経路から外れた最初の瞬間に壊れます。あるツールが不可逆な操作を行える場合、ヒューマン・イン・ザ・ループのチェックポイントは、最初の書き込みが顧客環境に届いた後ではなく、ループを配線する前に組み込みます。
7. **メモリースコープは、実装が最も簡単な方法ではなく、セッションの形によって決まる。**  
   コンテキスト内メモリーは書くのが最も簡単なパターンであり、それこそが、本番環境のセッションが開発時に使っていた長く継続したセッションよりも短く数が多いと分かったとき、最も早く破綻するパターンでもあります。外部ストレージはレイテンシを増やしますが、状態はセッションをまたいで保持されます。要約されたメモリーはコストを削減しますが、要約用プロンプトが保持しなかったものはすべて失われます。そしてステートレスは、完了して終了するジョブに適しています。本番環境の圧力の下でコンテキスト内から外部ストレージへリファクタリングするには約1時間かかりますが、設計時に同じ選択を意図的に行うには約20分で済みます。繰り返し使う指示をタスクをまたいで持ち越すことは、状態を持ち越すこととは別の問題であり、それに対応するパターンがSkillです。これは、すべてのセッションに注入される指示ではなく、その説明との一致によってClaudeが必要に応じて読み込むマークダウンファイルです。
8. **取り込み用のコードを書く前にマルチモーダルな入力のコストを計算し、ワークロードに合ったAPIを選ぶ。**  
   画像のコストは `⌈幅 / 28⌉ × ⌈高さ / 28⌉` ビジュアルトークンであり、画像1枚あたりの上限はモデルの階層によって異なります。最新モデルにおける高解像度の元画像は、テスト用データセットのサムネイルの何倍ものコストがかかることがあるため、この計算式は、手元にある入力ではなく、本番環境で想定される最大の入力に対して適用する必要があります。インラインのbase64は一度限りの画像に適し、Files APIは複数のリクエストで再利用されるアセットに適し、Message Batches APIは、非決定的なレイテンシと引き換えに、より低いトークンあたりのコストでオフラインの作業を処理します。避けるべき誤りは、同期APIをループの中で呼び出し、それをバッチ処理だと見なしてしまうことです。
